GUIDED ROADMAP · BEGINNER TO ADVANCED

Hardware Verification & Automation

Learn the engineering workflow around RTL: version control, self-checking tests, regression automation, build scripts, processor-level execution and continuous integration. These exercises are designed as hands-on tasks; they do not assume that Git, Linux or CI knowledge is already familiar.

Open interactive tooling exercise →

How to use this roadmap: work in a separate practice repository. For each exercise, save the command or file you created, run the check, and write down what a failure looks like. RTL simulation tasks can use your normal simulator; shell, Python and GitHub Actions tasks need a local development environment or a practice repository.

Stage 1 — Git and project workflow

Exercise 01 · Beginner

Create a repository and commit an RTL module

Create a repository for a simple counter. Add the RTL and its testbench, then make a commit with a descriptive message.

  1. Run git init in the project directory.
  2. Add a README.md describing the module and how to test it.
  3. Use git status, git add and git commit.

Deliverable: a clean initial commit and a README with reproducible test instructions.

Exercise 02 · Beginner

Review an RTL diff and use a feature branch

Change the counter reset behaviour on a branch. Use a diff to identify exactly what changed before committing.

  1. Create a branch with git switch -c fix/counter-reset.
  2. Change one behaviour and inspect git diff.
  3. Commit the change, then compare it with the base branch.

Deliverable: a small reviewable change with no unrelated edits.

Stage 2 — Testbench fundamentals

Exercise 03 · Beginner

Write a self-checking testbench

Verify a counter reset, increment and hold behaviour. The testbench must compare actual outputs with expected values and print an unambiguous pass or fail result.

  1. Drive reset and clock stimulus.
  2. Check values after the correct clock edge.
  3. Make a deliberate RTL error and confirm the test fails.

Deliverable: a testbench that detects at least one injected bug.

Exercise 04 · Beginner

Make a regression runner

Run three independent test cases from one command. A single failing test must make the overall regression fail.

  1. Separate the test cases or simulator invocations.
  2. Collect each result and a final pass/fail count.
  3. Return a nonzero process exit code if any test fails.

Deliverable: one command runs all tests and correctly signals failure to other tools.

Stage 3 — Build automation

Exercise 05 · Intermediate

Compile and simulate from a shell script

Create a script that compiles the RTL and testbench, runs the simulator, and stops immediately if compilation or simulation fails.

  1. Use a predictable build/output directory.
  2. Check command exit codes.
  3. Print a concise summary at the end.

Deliverable: a repeatable script that works from a fresh checkout.

Exercise 06 · Intermediate

Parse logs with Python

Write a Python script that reads a regression log and reports passed tests, failed tests and tests with no result. Do not treat a missing result as a pass.

  1. Read a log file supplied as a command-line argument.
  2. Recognise explicit pass/fail markers.
  3. Exit nonzero if a failure or incomplete test is found.

Deliverable: a machine-readable summary and reliable exit status.

Stage 4 — Processor-level execution

Exercise 07 · Intermediate

Compile a small RISC-V program to ELF

Use a RISC-V cross-compiler to build a tiny program. Inspect the ELF, then extract the program image for a simulation testbench.

  1. Compile a minimal C or assembly program for RV32I.
  2. Inspect the result with an ELF utility such as file or readelf.
  3. Use the toolchain's objcopy to produce a binary or memory image.

Deliverable: a reproducible build command and a generated program image.

Exercise 08 · Intermediate

Run the ELF through a simulation harness

Load the generated program image into a processor testbench and define a reliable completion protocol. Distinguish program failure from timeout or simulator failure.

  1. Load the image into instruction memory.
  2. Define a PASS/FAIL signature or completion address.
  3. Add a timeout and include useful diagnostics.

Deliverable: an end-to-end test that fails clearly when the program does not complete correctly.

Stage 5 — Continuous integration

Exercise 09 · Advanced

Create a GitHub Actions smoke-test workflow

Add a workflow that runs on pushes and pull requests, installs or selects the required simulator, and runs one small test.

  1. Create a workflow file under .github/workflows/.
  2. Use explicit build and test steps.
  3. Make a deliberately failing test and confirm the workflow goes red.

Deliverable: an automated CI run whose status reflects the test result.

Exercise 10 · Advanced

Debug CI from logs and artifacts

Diagnose a deliberately broken workflow. Find the first failing step, decide whether it is a source, configuration, dependency or test failure, and make the smallest safe fix.

  1. Read the failed job and step logs.
  2. Download an uploaded log or report artifact when available.
  3. Fix the cause and rerun the workflow; do not mark it passed based only on compilation.

Deliverable: a passing rerun and a short root-cause note explaining the failure.

Capstone: combine the regression runner, RISC-V ELF harness and GitHub Actions workflow into one pipeline. The final result should compile, execute, report failures accurately and retain logs that another engineer can use to reproduce a failure.
